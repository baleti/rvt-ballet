# Partition stream framing (measured on Autodesk samples 2018-2026; rvtballet/elemindex.py)

Nothing in a .rvt stores a per-element byte position (Global/ElemTable columns, Global/Latest, History, PartitionTable all tested: no equality, no correlation). Elements are found through a persistent index built from the framing below.

Stream `Partitions/N` (CFB stream, payload = 64896-byte pages, 353-byte trailers stripped):

    [20-byte head: u32 9, u32 0, u32 x, u32 at +14 = element count of THIS partition, u16 tag]
    repeat:
      [24-byte segment header: u32 kind(4..9), u32 y, u32 stored_len, u32 word3 (~128 KB, NOT the inflated length), u32 0x65/0x66, u32 0]
      [gzip member: 10-byte header, raw deflate, CRC32, ISIZE]
      [8-byte footer: u16 tagA, u32 stored_len (== header word 2), u16 tagB]      <- inside stored_len
      (stored_len covers member + footer)
    raw interludes (text, GUIDs, producer record) may sit between runs of segments
    tail: zero padding + producer record ("Data generated by Autodesk Revit") + variable-length (4-350 B) high-entropy run

Facts a writer must respect
- Segments inflate independently (about 128 KB each); ElementHeader records (category, owner view, family) are in a dense region at the START of each partition (1-5 percent of bytes).
- Changing one segment's compressed length changes `stored_len` in the header AND the footer, and shifts all later segments (nothing refers to offsets). Slack goes into zero padding before the tail record.
- Partition head count: deltas must agree with the Global/ElemTable row-count delta (sums only equal in single-partition files).
- The tail high-entropy run changes in every writer output seen; whether Revit verifies it is unverified (VM request in NEEDS-FROM-RVTOFFSET.md).

Gates: `elemindex.verify_partition` (CRC/ISIZE, footer, tiling, interlude hash) and `elemindex.compare_partitions` (original vs output; edits, adds, removals; interludes; head count). Tests: tests/test_elemindex.py (corruption escape tests).
