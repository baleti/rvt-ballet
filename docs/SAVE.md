# Saving from rvt-ballet (SAVE AS / SAVE / edits)

Status: offline-verified with the savegate library. Revit evidence so far (shared write-lab harness, Revit 2024, audit OFF, synthetic write-lab scene only): all six viewer-produced edited files opened at least once (three single edits incl. unicode and a 200-character value, and generations 1, 4 and 8 of an eight-save chain; several needed retries because of guest failures). Failures seen were guest/transport problems (the unmodified original also failed twice). Revit 2026: four viewer-edited 2026 files also opened (a single edit and generations 1-3 of a chain, including the re-paged generation 3; the unmodified control opened 2/2). Audit-ON (SaveAs + reopen element lists equal in every case): all four Revit 2026 files passed (single edit and generations 1-3 of the chain incl. the re-paged gen3), each on the first attempt; Revit 2024 single0 and single1 passed (others hit guest failures, the unmodified control passed audit-on on its 2nd try). The layout guard is therefore a precaution without Revit evidence of harm. NOT yet done: audit-ON opens, more 2026 edits, real client projects, edit kinds other than string parameters. Overwrite stays disabled by default.

Requires `~/src/savegate` (or an installed `savegate`) and the write-lab (`~/rvt-research/write-lab`, env `RVTBALLET_WRITELAB`). Without them the viewer runs unchanged and every save endpoint answers 501.

Writable Revit years: those in `savegate.adapters.RVT_WRITABLE` (2024, 2026 today). Other years are refused with HTTP 415 naming the version and the list.

## Endpoints (all per model id `mid`)
| endpoint | purpose |
|---|---|
| `GET /api/m/{mid}/saveinfo` | opens the save session (fingerprint = load time): `{available, open, version, size, sha256, allow_overwrite, gate_open, pending_edits}` |
| `POST /api/m/{mid}/edit` `{op:'set_string', eid, value, field?, match?}` or (rvtedit backend only) `{op:'set_num', eid, param|pid, value, kind:'Double'|'Int'}` | record an edit (trial-replayed at once); fields: ParamValueAString.m_value, DatumPlane.m_text, DBView.m_viewName, SymbolInfo.m_name |
| `POST /api/m/{mid}/edit/undo`, `GET /api/m/{mid}/edits` | pop / list pending edits (memory only, dropped on viewer restart) |
| `POST /api/m/{mid}/saveas` `{dest, overwrite?}` | write a copy; never touches the source; returns dest, size, sha256[:12], backup, verify report |
| `POST /api/m/{mid}/save` `{force?, confirm?}` | overwrite the source (needs `RVTBALLET_ALLOW_OVERWRITE=1` **and** an open oracle gate); `force` needs `confirm:true` |
| `GET /api/m/{mid}/backups`, `POST /api/m/{mid}/restore` `{n, confirm:true}` | list / restore backups (current file is backed up first) |
| `GET /api/recover` | journals of sessions that never closed (crash / kill) |

Error codes (JSON `{ok:false, code, error, report?}`): `bad_dest` 400, `edit_error` 400, `conflict` 409 (file changed since load), `gate_closed` / `overwrite_disabled` / `exists` 409, `locked` 423 (another save running or lock held), `verify_failed` 422, `output_unreadable` 422, `layout_changed` 409 (overwrite refused when a partition stream's page layout would change: SAVE AS warns instead; override RVTBALLET_ALLOW_LAYOUT_CHANGE=1), `too_big` 507, `bad_dest` 400 (output differs outside the declared edit; nothing written; `report.unexpected` lists the first keys), `unsupported_version` 415, `disk_error` 507, `unavailable` 501.

Multi-partition files: the rvtedit backend groups operations by the partition each element lives in and applies them as sequential passes (as rvtedit's own command line does); before this a move of an element outside the default partition of a real project was refused with 'lives in Partitions/X'.

Edit backend: `RVTBALLET_EDIT_BACKEND=wledit` (default, write-lab `Editor`) or `rvtedit` (edit-lab `rvtedit.Edit`, same string edit; path `RVTBALLET_EDITLAB`). One string edit gives byte-identical output on both; with two edits the bytes differ (parameter values read back identical, one element's record hash differs: open question for rvtedit2). `{op:'set_string', eid, param|pid, value}` edits a string parameter by NAME or id (rvtedit backend only; ambiguous names such as 'Description' with two ids on the element are refused): this is what removes the old ambiguity of 'the first value with this text'. `set_num` is wired (rvtedit backend only; a parameter NAME is resolved to the single id stored on that element, ambiguous or not-stored names are refused with 400; values are in Revit internal units, e.g. feet for lengths). `move` (`{op:'move', eid, dx, dy, dz}` in feet, rvtedit backend) is wired and tested offline; `delete` is wired but opt-in (`RVTBALLET_ENABLE_DELETE=1`) and currently refused by verify on the test element (neighbour orphaned, see QUEUE item 48); `rotate` (`{op:"rotate", eid, deg}`, degrees about the instance origin, rvtedit backend) is wired and tested offline (QUEUE 59; one real FamilyInstance rotation passed Revit 2026 audit ON). Revit evidence (2026 guest, audit ON, SaveAs+reopen equal): set_num on a Floor-type element and move of a FamilyInstance each passed on the first attempt; 2024 set_num also passed (second run); 2024 move pending; delete has none on synthetic scenes; on REAL projects (2024, opened as a 2026 upgrade) deleting ONE leaf FamilyInstance (nothing depends on it, single record) passed offline verify and Revit 2026 audit ON on 2 projects (7.6 and 25 MB, 1 element each). Non-leaf deletes are still refused by verify (neighbour orphaned). Numeric edits on real projects (QUEUE 58): Double on 2 projects and Int (a floor's Structural) on 1 passed Revit audit ON; Int on VIEWS is refused (the reader derives view parameters onto viewports/arrows), and any edit on an element that has records in several partitions cannot be read back (the reader shows the older copy): moves/parameter edits are refused by the guards, rotate is refused up front (QUEUE 59e/f).

Inspector editing: with the server started as `RVTBALLET_EDIT_BACKEND=rvtedit` the inspector shows a pencil on string-valued parameter rows (never on numbers, UniqueId, names); an edit is recorded as a pending edit (header button `Undo edit (n pending)`), and nothing is written until Save as / Save. saveinfo reports `name_edit`.

Verification worker: the element dump of the verify runs in a CHILD process under a hard address-space limit (`RVTBALLET_SNAPSHOT_MEM_GB`, default = the viewer's remaining budget, min 2 GB; `RVTBALLET_SNAPSHOT_WORKER=0` runs it in-process). A model that does not fit kills the worker and the save is refused with `too_big` (HTTP 507, nothing written); reader errors inside the worker still give `output_unreadable`. This is the real protection against running the machine out of memory; the pre-check below is only an early, cheap estimate.

Limited verification (opt-in, SAVE AS only): `POST /api/m/{mid}/saveas {dest, light_verify:true, confirm:true}` skips the element dump and checks structure only (`rvtballet/lightverify.py`: same streams, untouched streams byte-identical, same gzip member count, at most 4 changed members per edit, nothing outside the members changed except trailing padding). It is much cheaper (a 64 MB real project that the full verify could not finish saved in ~6.7 min, 1 member changed) but it cannot show that the changed member is the declared element and it says so in the result (`limited_verification`, warning). Never available for SAVE (overwrite). In the UI, when a SAVE AS is refused as `too_big` the result panel offers a button `Save with limited verification`, which asks for confirmation with the limits spelled out before re-sending the request with `light_verify` and `confirm`.

Memory guard: the save session is refused up front (`too_big`, HTTP 507, `saveinfo.open=false`) when the estimated need exceeds the viewer's budget (`RVTPLAT_MEM_GB` or 70% of RAM). Estimate = max(9 x file size, 200 KB x element rows); element rows come from the decompressed `Global/ElemTable` size / 28. Basis: real 2024 projects used ~170 KB/row (24 MB file, ~26k rows, 4.5+ GB) and the largest tried so far kept growing past 8.6 GB; the factors are conservative and tunable (`RVTBALLET_SAVE_MEM_FACTOR`, `RVTBALLET_SAVE_MEM_PER_ROW_KB`). A save on a real project takes minutes (12 s - 13 min for 7.6 - 24 MB files).

## Guarantees checked by tests (`tests/run_save.sh`, ~2 min)
Source never changes on SAVE AS; atomic write with backup; element-level verify of every output (declared edits only); crash at each step and ENOSPC leave source/target consistent; concurrent saves refused; hostile destinations refused before any work.

## Not guaranteed / open
Revit opening outputs beyond the four files above (audit-on, 2026, real projects); edits other than string fields; edits whose dependents change (e.g. Level rename: refused by verify); parameter edits addressed by name (writer op missing, so the UI has no edit control); Windows/macOS behaviour.


## Evidence by value in Revit (2026-10-31)
Opening and auditing an output proves it is a valid file, not that the edit did what was asked. With the Revit API readback tools (`tools/rvtsave_readback.py` location/group/mark, `tools/rvt_rotation_readback.py` rotation, `tools/rvt_param_readback.py` parameter values; Revit 2026 guest, audit ON, 2024 real projects opened as upgrades) these edits were read back BY VALUE on real projects: move +1 ft (exactly +1, also on the element that lives in two partitions: Revit honours the newest copy), rotate 30 deg (30.0000), Double Width Factor 1 -> 1.25, wall Base Extension Distance 0 -> 0.25 ft (Revit shows 76 mm; neighbouring wall parameters unchanged), Int Section Shape 0 -> 8, Int Coarse Scale Fill Color 0 -> 8421504, string Comments to a non-ASCII value (UTF-16 DC,6E,EF,20,2713 exact, 2 chains), view Detail Level 1 -> 2 (the echoed viewport/viewer also reads 2), Family Section Shape 0 -> 8 (its symbol too), Floor Structural 1 -> 0, three leaf deletes (id present before, missing after; one at a real location), fuzz-chain moves (3/3, control unchanged). NOT visible in Revit: LeaderStyle Heavy End Pen Weight (stored int 1 -> 2, Revit shows 6 before and after: the file is audit-clean, the edit is a no-op for Revit). Limits: 2 real projects, one edit of each kind, nothing on 2025/2026 real files, no Windows/macOS.
