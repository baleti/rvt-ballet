
### Type swap on a family instance (Revit-made c3xtsany24, Snowdon Structural 2024, 588559: 588556 -> 588537)
Revit changes FamilyInstance.m_masterSymbolId (588556 -> 588537) AND InstInfoBase.m_symbolId (984678 -> 1028040): a NEW derived-symbol element 1028040 is added (16571 -> 16572 elements), instance 588537 header changes. Writer change_type (same ids, offline) changes only m_masterSymbolId (m_symbolId stays 984678, the old type's derived symbol). Gap: stale m_symbolId; whether Revit tolerates it is being tested by opening the writer output in the VM (c3xtsanywriter24).
Derived symbol anatomy (984678 old vs 1028040 new, Revit 2024 after-file, field-level): same field sequence (1289 vs 1287 fields) but it is a geometry-bearing clone: FamilySymbol.m_masterId = the type (588556 / 588537), GeomRef.m_geomTag, GTagDirFlagsPair.m_tag, m_controlIconTags and Outline.m_minmax all differ (different bbox of the target type). So it cannot be built by cloning the old derived symbol with new ids; it is derived data of the target type's geometry. Candidate writer strategy (untested): point InstInfoBase.m_symbolId at an EXISTING derived symbol whose m_masterId == target type (only when one exists), else leave change_type gated. Needs a Revit-made pair with a target type that already has a derived symbol.
